Cómo se conecta. Todas las llamadas usan rutas relativas (environment.apiUrl = '') que en desarrollo atraviesa proxy.conf.json hacia el gateway (http://localhost:8082; rutas /auth y /users).
  • Bearer automático: authTokenInterceptor agrega Authorization: Bearer <accessToken> a toda petición salvo /auth/login, /auth/refresh y /auth/logout (públicos). Un 401 en cualquier otra llamada invalida la sesión y redirige a /login.
  • Errores de negocio: el backend responde { "error": string, "code": string }; httpErrorAlertInterceptor muestra una alerta por code (catálogo en auth-errors.ts), salvo los que ya tienen UI propia (INVALID_CREDENTIALS, ACCOUNT_LOCKED, SESSION_IDLE_TIMEOUT).
  • Autorización en el servidor: /users/** exige rol ADMIN o ALTAS (SecurityConfig.java); un 403 sin code es ese rechazo.

3. Detalle por endpoint

3.1 Autenticación (/auth/*)

POST/auth/loginPúblico
Request{ username, password }
Respuesta 200{ accessToken, refreshToken, expiresIn (s), user: UserSummaryDto } — user incluye roles, permissions, subsidiarias, ubicaciones, mustChangePassword
Errores401 INVALID_CREDENTIALS · 423 ACCOUNT_LOCKED (5 intentos fallidos)
FrontAuthService.login() → Login.onSubmit(); después completeLogin() guarda la sesión en sessionStorage
POST/auth/refreshPúblico
Request{ refreshToken }
Respuesta 200{ accessToken, refreshToken, expiresIn } — el refresh anterior queda invalidado (rotación)
Errores401 INVALID_REFRESH_TOKEN · REFRESH_TOKEN_REUSED · REFRESH_TOKEN_EXPIRED · SESSION_IDLE_TIMEOUT (30 min sin actividad) · USER_LOCKED_OR_INACTIVE
FrontAuthService.refreshAccessToken() (privado), disparado por un timer 30 s antes de que expire el access token. SESSION_IDLE_TIMEOUT cierra sesión y muestra el aviso de inactividad.
POST/auth/logoutPúblico
Request{ refreshToken }
Respuesta 200{ success: true }
FrontAuthService.logout() (menú lateral y header). Best-effort: la sesión local se cierra aunque la llamada falle.
GET/auth/meBearer
Respuesta 200UserSummaryDto (id, email, displayName, phone, status, roles, permissions, subsidiarias, ubicaciones, mustChangePassword, lastLoginAt, emailVerified)
FrontAuthService.me() / validateResumedSession(): al recargar la página revalida la sesión restaurada y refresca roles/permisos/catálogos. Los permisos efectivos del portal salen de este arreglo.
POST/auth/change-passwordBearer
Request{ currentPassword, newPassword }
Respuesta 200{ success: true }
Errores401 INVALID_CREDENTIALS (contraseña actual incorrecta). Mientras mustChangePassword sea true, el resto de endpoints protegidos responde 403 PASSWORD_CHANGE_REQUIRED.
FrontAuthService.changePassword() → pantalla /cambiar-password (authGuard la fuerza antes de cualquier otra ruta)

3.2 Administración de usuarios (/users/*) — rol ADMIN o ALTAS

GET/usersLista paginada
Querypage (0) · size (100) · search? · role? · status? (ACTIVE|INACTIVE|LOCKED)
Respuesta 200{ content: UserSummaryDto[], page, size, totalElements, totalPages }
FrontUserManagementService.syncFromBackend(), al entrar a /usuarios: reconcilia roles/permisos/estado/último acceso/subsidiarias/ubicaciones de cada cuenta conocida y agrega las cuentas reales que el mock no tiene (pidiendo su detalle).
GET/users/{id}Detalle completo
Respuesta 200UserDetailDto: firstName, lastName, displayName, createdAt, birthDate, ssn, gender, address{city,state,postalCode,street1,street2,interiorNumber,exteriorNumber}, department, area, jobTitle, manager{id,displayName}, employeeCode, hireDate, contractEndDate, temporaryPassword + los campos de UserSummaryDto
Errores404 USER_NOT_FOUND
FrontUserDetail (carga y fusiona sobre el registro local; se vuelve a pedir tras cada mutación) y syncFromBackend() para cuentas nuevas. temporaryPassword solo llega mientras mustChangePassword sea true.
POST/usersAlta de usuario
Request{ firstName, lastName, email, phone, supervisorId, subsidiariaIds[], ubicacionIds[], roleIds[], status: "ACTIVE"|"INACTIVE" } — roleIds solo se respeta con el permiso manage_roles
Respuesta 201{ id, email, displayName, roles, permissions, subsidiarias, ubicaciones, mustChangePassword, temporaryPassword } — la contraseña temporal solo se devuelve aquí
Errores409 EMAIL_ALREADY_REGISTERED · 400 INVALID_ROLE / INVALID_USER_STATUS · 403 ROLE_ASSIGNMENT_FORBIDDEN
FrontUserManagementService.createUser() ← formulario /usuarios/nuevo (roles, subsidiarias y ubicaciones múltiples; supervisor select simple)
PATCH/users/{id}Edición parcial
Request{ firstName, lastName, email, phone, birthDate, ssn, gender, address, department, area, jobTitle, managerId, employeeCode, hireDate, contractEndDate } — solo sobreescribe lo no nulo. No incluye estado, roles, subsidiarias ni ubicaciones.
Respuesta 200UserSummaryDto (no repite los campos enviados)
Errores404 USER_NOT_FOUND · 409 EMAIL_ALREADY_REGISTERED
FrontUserManagementService.updateUserProfile() ← "Guardar cambios" de Información general
PATCH/users/{id}/statusCambio de estado
Request{ status: "active" | "inactive" | "blocked" } (minúsculas; blocked = enum LOCKED)
Respuesta 200UserSummaryDto — aquí status vuelve en mayúsculas (ACTIVE|INACTIVE|LOCKED)
Errores400 INVALID_USER_STATUS · 404 USER_NOT_FOUND
FrontUserManagementService.setStatus() ← chip de estado en la lista y en el detalle (con confirmación)
POST/users/{id}/verify-emailVerificación manual
RequestSin cuerpo
Respuesta 200{ id, emailVerified: true } — fuerza el flag sin validar token pendiente
FrontUserManagementService.setEmailVerified() ← "Marcar como verificado" en Seguridad y acceso
PATCH/users/{id}/unlockDesbloqueo
RequestSin cuerpo
Respuesta 200Cuenta desbloqueada (ACTIVE, contador de intentos en 0); el front no usa el cuerpo
Errores403 (sin rol ADMIN/ALTAS, sin code) · 404 USER_NOT_FOUND
FrontUserDetail.onUnlockBackendClick() ← "Desbloquear cuenta" (campo "Cuenta real (backend)")

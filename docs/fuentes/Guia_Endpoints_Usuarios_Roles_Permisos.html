Cómo está armado

  • Gateway (puerto 8080): es el único punto de entrada. Valida que el token JWT sea auténtico y no haya vencido, responde el CORS del navegador y reenvía la petición al servicio correspondiente.
  • Auth Service (puerto 8081): no es accesible desde fuera; vuelve a validar el token por seguridad y aplica los permisos de cada endpoint. Es quien guarda usuarios, roles, permisos y bitácora.
  • Base de datos: PostgreSQL compartida. El esquema lo crea únicamente el módulo db-migration; el Auth Service solo lo valida al arrancar.
  • Front: dos interceptores funcionales (withInterceptors([authTokenInterceptor, httpErrorAlertInterceptor])): el primero agrega el Bearer a todo lo que va al backend salvo /auth/login, /auth/refresh y /auth/logout; el segundo avisa los errores del backend (sección 5).

Conceptos que se repiten en todo el documento

Formato de los errores

El Auth Service responde siempre { "error": "mensaje", "code": "CODIGO" }. El Gateway, cuando rechaza por token ausente, vencido o contraseña pendiente, usa el formato estándar de Spring ({ "timestamp", "status", "error", "path" }), sin código ni mensaje. El front decide siempre por code (estable), nunca por el texto de error; el único texto del back que se muestra tal cual es el de ACCOUNT_LOCKED, porque trae los minutos restantes.

1. Sesión y autenticación

POST/auth/loginIniciar sesión
Para qué sirveEs la pantalla de inicio de sesión. Entrega al front todo lo necesario para trabajar: los tokens y los datos del usuario (roles, permisos, subsidiarias, ubicaciones).
Qué haceValida el correo y la contraseña, abre una sesión y devuelve un par de tokens más el resumen del usuario. Cuenta los intentos fallidos y bloquea la cuenta al quinto.
Cómo lo hace
  • Busca al usuario por correo (solo los que no están dados de baja). Si el correo no existe responde lo mismo que una contraseña mala, para no revelar qué correos existen.
  • Si el usuario estaba bloqueado temporalmente y ya pasaron las 2 horas, lo desbloquea antes de seguir (y deja constancia en la bitácora).
  • Si sigue bloqueado responde 423 aunque la contraseña sea correcta, indicando cuántos minutos faltan.
  • Compara la contraseña contra su hash bcrypt (la contraseña nunca se guarda en claro).
  • Si falla, suma un intento en una transacción aparte para que el conteo se guarde aunque el login termine con error. Al quinto intento marca la cuenta como bloqueada por 2 horas.
  • Si acierta, reinicia el contador, registra la fecha de último acceso y genera los tokens: un JWT firmado (HS256, 15 min) y un refresh token aleatorio (8 h) del que solo se guarda el hash.
Petición
POST /auth/login
{ "username": "laura.gomez@cocteldelmar.com", "password": "Passw0rd!" }
(el campo "username" lleva el correo)
Respuesta
{ "accessToken": "eyJhbGciOi...", "refreshToken": "q8Zk...", "expiresIn": 900,
  "user": { "id": 12, "email": "laura.gomez@cocteldelmar.com", "displayName": "Laura Gomez",
    "phone": "3001234567", "status": "ACTIVE",
    "roles": ["CONTABILIDAD"], "permissions": ["view_dashboard"],
    "subsidiarias": [{"id": 1, "nombre": "..."}], "ubicaciones": [{"id": 7, "nombre": "..."}],
    "mustChangePassword": false, "lastLoginAt": "2026-10-06T19:04:03Z", "emailVerified": true } }
Errores401 INVALID_CREDENTIALS · 423 ACCOUNT_LOCKED (el mensaje dice cuánto falta para poder reintentar).
OjoexpiresIn está en segundos. Si mustChangePassword es true, el usuario debe cambiar su contraseña antes de usar la app.
En el front Implementado y ajustado AuthService.login · Login.onSubmit
  • Cambio v2.0: el 423 / ACCOUNT_LOCKED ya no muestra un texto fijo: Login.onSubmit muestra el error que manda el back (serverErrorText() en auth-errors.ts), que incluye los minutos restantes del bloqueo temporal o indica contactar al administrador si el bloqueo es manual. El texto fijo (BLOCKED_MESSAGE) queda solo de respaldo.
  • 401 → "Usuario o contraseña inválidos."; sin respuesta (status 0) → mensaje de conexión. INVALID_CREDENTIALS y ACCOUNT_LOCKED los pinta el propio formulario, por eso el interceptor no duplica el aviso.
  • expiresIn (segundos) programa el refresh proactivo; si mustChangePassword es true se redirige a /cambiar-password.
POST/auth/refreshRenovar los tokens
Para qué sirveMantiene viva la sesión sin pedir la contraseña otra vez. El front lo llama antes de que venza el accessToken.
Qué haceCambia un refresh token vigente por un par nuevo (accessToken y refreshToken).
Cómo lo hace
  • Busca el token por su hash. Si no existe: INVALID_REFRESH_TOKEN.
  • Si el token ya se había usado (está revocado) lo trata como robo: cierra todas las sesiones del usuario y responde REFRESH_TOKEN_REUSED.
  • Si pasaron las 8 h: REFRESH_TOKEN_EXPIRED. Si pasaron más de 30 minutos desde la última actividad: SESSION_IDLE_TIMEOUT (inactividad).
  • Si el usuario ya está bloqueado o inactivo: USER_LOCKED_OR_INACTIVE.
  • Si todo está bien emite un par nuevo (con los roles y permisos actuales de la base) y revoca el anterior.
Petición
POST /auth/refresh
{ "refreshToken": "q8Zk..." }
Respuesta
{ "accessToken": "...", "refreshToken": "...", "expiresIn": 900 }
Errores401 con INVALID_REFRESH_TOKEN, REFRESH_TOKEN_EXPIRED, REFRESH_TOKEN_REUSED, SESSION_IDLE_TIMEOUT o USER_LOCKED_OR_INACTIVE.
OjoNunca lances dos renovaciones al mismo tiempo con el mismo token: la segunda se interpreta como robo y cierra todas las sesiones. Esta es también la forma en que el usuario recibe sus permisos actualizados.
En el front Implementado AuthService.refreshAccessToken · requestTokenPair
  • Un solo refresh en vuelo (timer en scheduleRefresh); requestTokenPair es el único punto que llama al endpoint y lo comparten el refresh programado y el de change-password.
  • Cualquier 401 de este endpoint cierra la sesión; SESSION_IDLE_TIMEOUT la cierra con el aviso de inactividad en el login. REFRESH_TOKEN_REUSED lo avisa el interceptor de errores.
POST/auth/logoutCerrar sesión
Para qué sirveEl botón "Cerrar sesión".
Qué haceInvalida el refresh token de la sesión actual para que no pueda renovarse más.
Cómo lo hace
  • Marca el token como revocado. Si el token no existe responde igual con éxito (es idempotente).
  • No exige un accessToken vigente a propósito: así se puede cerrar sesión aunque el token ya haya vencido.
Petición
POST /auth/logout
{ "refreshToken": "q8Zk..." }
Respuesta
{ "success": true }
Errores—
OjoEl accessToken que ya se emitió sigue siendo válido hasta que venza (máximo 15 min); lo que se impide es renovarlo.
En el front Implementado AuthService.logout
  • Se llama "fire and forget" y la sesión local se limpia siempre; es ruta pública en authTokenInterceptor (no lleva Bearer).
GET/auth/meDatos de la sesión actual
Para qué sirveAl recargar la página, el front necesita saber quién es el usuario sin pedir la contraseña otra vez.
Qué haceDevuelve los mismos datos del campo user del login.
Cómo lo hace
  • Toma el id del usuario del token (nunca de un parámetro que el cliente pueda falsificar) y lee sus datos actuales.
  • Es una de las tres rutas permitidas mientras la contraseña temporal no se haya cambiado.
Petición
GET /auth/me
Respuesta
{ "id": 12, "email": "...", "displayName": "...", "roles": [...], "permissions": [...], ... }
Errores401 si el token venció o es inválido.
En el front Implementado AuthService.me
  • validateResumedSession la usa al recargar la página para validar la sesión guardada en sessionStorage.
POST/auth/change-passwordCambiar la contraseña
Para qué sirvePantalla de cambio obligatorio de contraseña (primer ingreso o después de un reinicio) y cambio voluntario.
Qué haceReemplaza la contraseña del usuario autenticado y apaga la marca de contraseña pendiente.
Cómo lo hace
  • Comprueba que la contraseña actual coincida con el hash guardado.
  • Guarda el hash bcrypt de la nueva (mínimo 8 caracteres) y pone mustChangePassword en false.
Petición
POST /auth/change-password
{ "currentPassword": "LAURAGOMEZ2026", "newPassword": "NuevaClave2026" }
Respuesta
{ "success": true }
Errores401 INVALID_CREDENTIALS (la actual no coincide) · 400 (la nueva es muy corta).
OjoEl token que ya tiene el usuario sigue marcado como "contraseña pendiente". Hay que llamar a /auth/refresh justo después para obtener uno limpio.
En el front Implementado y ajustado AuthService.changePassword · ChangePassword
  • Cambio v2.0 — refresh posterior: changePassword() encadena (switchMap) un POST /auth/refresh con el refresh token vigente y reemplaza la sesión (rotateSessionAfterPasswordChange, mustChangePasswordHint: false). Si ese refresh falla, se invalida la sesión (idle_timeout / invalid_token).
  • Cambio v2.0 — 401 de negocio: authTokenInterceptor ya no cierra la sesión ante un 401 con INVALID_CREDENTIALS (contraseña actual incorrecta); antes un error de tecleo sacaba al usuario.
  • ChangePassword maneja 401 ("La contraseña actual es incorrecta."), 400 (nueva con menos de 8 caracteres), 0 (sin conexión) y un mensaje genérico para el resto.
  • Verificado en navegador: contraseña actual incorrecta → la sesión se mantiene; cambio correcto → el refresh token rota y aterriza en la pantalla de inicio.

2. Administración de usuarios

Todos estos endpoints exigen el permiso manage_users, salvo los que indican otro. El Gateway valida el token y el Auth Service vuelve a comprobar el permiso: si falta responde 403.

GET/usersListar y buscar usuarios
Para qué sirveLa tabla principal de "Administración de usuarios", con búsqueda, filtros y paginación.
Qué haceDevuelve una página de usuarios. Los usuarios dados de baja no aparecen.
Cómo lo hace
  • Construye la consulta con filtros opcionales: search (texto en el nombre completo o el correo, sin importar mayúsculas), role (código del rol) y status (active, inactive, blocked).
  • Pagina en la base de datos (page empieza en 0, size por defecto 20).
  • Resuelve las subsidiarias y ubicaciones de cada fila para mostrarlas con nombre.
Petición
GET /users?search=laura&role=CONTABILIDAD&status=active&page=0&size=20
Respuesta
{ "content": [ { "id": 12, "email": "...", "displayName": "Laura Gomez", "status": "ACTIVE",
    "roles": ["CONTABILIDAD"], "permissions": ["view_dashboard"], ... } ],
  "page": 0, "size": 20, "totalElements": 25, "totalPages": 2 }
Errores403 (sin código) si falta el permiso manage_users.
Ojostatus=blocked incluye a los bloqueados por un administrador y a los bloqueados por intentos fallidos.
En el front Implementado y ajustado AuthService.listUsers · listAllUsers · UserManagementService.syncFromBackend
  • Cambio v2.0 — permiso, no rol: el front ya no habla de roles ADMIN/ALTAS (se eliminó forbiddenRoleMessage). El 403 sin código lo avisa httpErrorAlertInterceptor con un texto de falta de permiso.
  • Cambio v2.0 — paginación: size se mantiene en 100 (USERS_PAGE_SIZE) y AuthService.listAllUsers() recorre las páginas (0-based, totalPages) con expand + reduce. syncFromBackend() lo usa, así que con más de 100 cuentas no se pierden las siguientes.
  • Las cuentas del backend sin registro local se insertan pidiendo su detalle (fetchAndInsertUser); las del mock se reconcilian por backendUserId.

Qué haceDevuelve todos los datos del usuario, incluidos los contadores de seguridad.
Cómo lo hace

POST/usersDar de alta un usuario
Para qué sirveEl botón "Nuevo usuario". El administrador no escribe contraseña: el sistema genera una temporal.
Qué haceCrea al empleado, su cuenta de acceso, su pertenencia organizacional y, si se indica, sus roles.
Cómo lo hace
  • Rechaza el correo si ya lo usa otro usuario activo (un correo de un usuario dado de baja sí se puede reutilizar).
  • Asignar roles al crear exige el permiso manage_roles; sin él responde 403.
  • Valida que cada rol, subsidiaria y ubicación existan; si alguno no, rechaza todo sin guardar nada.
  • Al asignar un rol copia los permisos por defecto de ese rol al usuario.
  • Genera la contraseña temporal: NOMBRE + PRIMER APELLIDO + AÑO, en mayúsculas y sin acentos (Laura Gómez, 2026 = LAURAGOMEZ2026), la guarda con bcrypt y marca mustChangePassword.
  • Registra la acción created en la bitácora.

PATCH/users/{id}Editar datos personales y organización
Para qué sirveGuarda las pestañas Información personal y Organización en una sola llamada.
Qué haceActualiza solo los campos que llegan con valor; lo que no se manda no se toca.
Cómo lo hace
  • Cambiar el correo lo deja sin verificar y comprueba que no lo use otro usuario.
  • subsidiariaIds (pertenencia) y ubicacionIds (acceso al portal): una lista reemplaza la actual, una lista vacía las quita todas y omitirla no toca nada. Lo que se quita no se borra: queda con enabled = false.
  • Si un id de subsidiaria o ubicación no existe, rechaza la actualización completa (no se guarda ni el resto).
  • Registra updated y, si cambió la organización, también organization_updated.

PATCH/users/{id}/rolesGuardar roles y permisos
Para qué sirveEl botón "Guardar permisos" de la pestaña Seguridad y acceso.
Qué haceReemplaza los roles y/o los permisos de una persona. Los permisos son independientes del rol.
Cómo lo hace
  • Los dos campos son opcionales: omitido = no tocar; una lista reemplaza la actual por completo.
  • La regla "al cambiar de rol se restablecen los permisos por defecto" la aplica el front (usa defaultPermissions de GET /roles) y envía el resultado final; el backend lo guarda tal cual.
  • Cambiar roles exige el permiso manage_roles (se revisa el del usuario que hace el cambio).
  • Valida roles y permisos antes de guardar; si alguno no existe, no se guarda nada.
  • En la bitácora solo queda lo que cambió de verdad: role_changed y/o permissions_changed.
Petición
PATCH /users/12/roles
{ "roleIds": ["TESORERIA"], "permissions": ["view_reconciliation", "export_reports"] }
Respuesta
(resumen del usuario con sus roles y permisos nuevos)
Errores400 INVALID_ROLE · 400 INVALID_PERMISSION · 403 ROLE_ASSIGNMENT_FORBIDDEN · 404.
OjoEl usuario verá sus permisos nuevos en su próxima renovación de token (máximo 15 minutos).
En el front Pendiente en el front Hoy local: UserManagementService.changeRoles / setPermissions
  • No conectado. Para implementarlo: AuthService.updateRoles(), enviar el resultado final de la regla "cambio de rol → permisos por defecto" y, si el usuario editado es el propio, forzar un refresh.

  • blocked es un bloqueo manual: no vence solo, hay que activarlo de nuevo. Se guarda como LOCKED.
  • Registra status_changed en la bitácora.

Respuesta
(resumen del usuario; su "status" viene como ACTIVE, INACTIVE o LOCKED)

Reglas del interceptor de errores

  • Código con UI propia (INVALID_CREDENTIALS, ACCOUNT_LOCKED, SESSION_IDLE_TIMEOUT): el interceptor no muestra toast, para no duplicar el aviso del formulario de login / cambio de contraseña.
  • PASSWORD_CHANGE_REQUIRED: marca la sesión como "debe cambiar contraseña", muestra un aviso y redirige a /cambiar-password (si ya está ahí, no repite el aviso).
  • Cualquier otro código: toast con el mensaje del catálogo (o el genérico con el código).
  • 403 sin código (rechazo de Spring Security por falta de permiso, antes de llegar al manejador de errores del back): toast de "sin permiso".
  • 5xx sin código: toast de error del servidor.
  • 400 sin código (validación de campos): no se avisa en el interceptor; cada formulario decide el texto (p. ej. contraseña corta).
  • El interceptor siempre re-lanza el error: el subscribe({ error }) de quien llamó sigue corriendo (reactivar botones, cerrar modales).
  • authTokenInterceptor: un 401 en una llamada autenticada cierra la sesión (invalid_token, o idle_timeout si trae SESSION_IDLE_TIMEOUT), salvo INVALID_CREDENTIALS, que es un error de negocio (contraseña actual incorrecta).

6. Bloqueo por intentos fallidos

  • Al quinto intento fallido de login la cuenta se bloquea 2 horas. Mientras dure, el login responde 423 aunque la contraseña sea correcta, y el mensaje dice cuántos minutos faltan. El front muestra ese mensaje tal cual (v2.0).
  • Pasadas las 2 horas el usuario se desbloquea solo: al intentar entrar, o por un barrido automático cada minuto, lo que ocurra primero. Su contador de intentos vuelve a cero y queda constancia en la bitácora.
  • Un administrador puede desbloquearlo antes poniendo su estado en active (o con PATCH …/unlock, no documentado). El detalle del usuario muestra intentos fallidos y "Bloqueada hasta" (v2.0).
  • Un bloqueo manual (blocked) no vence solo: solo se levanta activando al usuario (lockedUntil llega null).
  • La duración (2 horas) es provisional y se cambia en la configuración del Auth Service.

7. Alcance de la verificación de v2.0

  • Verificado en navegador contra el backend local: mensaje de login con cuenta bloqueada (texto del back), contraseña actual incorrecta sin cierre de sesión, cambio de contraseña con rotación del refresh token, detalle con "Bloqueada hasta", multi-selects en modo edición y "Desbloquear cuenta".
  • No verificable con la pila local actual: el contenedor del backend se construyó desde feature/login, que no devuelve failedLoginAttempts / activeSessions / lockedUntil en el detalle, no incluye los minutos restantes en el 423 y no persiste subsidiariaIds / ubicacionIds en PATCH /users/{id}. El front los lee con valores por defecto (?? 0 / ?? null) y el código sigue la guía y el UpdateUserRequest de DEV. Hay que reconstruir la pila desde DEV para una prueba completa.
  • La paginación de GET /users (más de 100 cuentas) está implementada con el contrato totalPages de la guía; la base local tiene 30 cuentas, por lo que solo se ejercita la primera página.
